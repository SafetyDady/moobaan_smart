## Confirmed issues

1. Legacy `AccountingService.generate_aging_report` omits applied credits, uses stored invoice status and compares receipt timestamps to a date at month-end. On the pristine September report, it returns519,997.10 THB versus current canonical outstanding518,797.10: an actual1,200.00 overstatement. This confirms the old-report gap acknowledged in prior reviews; it should now be closed before releasing the full report package. Distinguish it from the active frontend's `/api/reports/invoice-aging`, which already deducts credits through the model but still filters by stored status. The current endpoint is not universally missing credit deductions.
2. `get_allocatable_ledgers` excludes POSTED ledgers without pay-ins through an inner join. Additionally, the main invoice apply API rejects missing/non-ACCEPTED pay-ins. Fixing only the list would make a selectable item fail on submit. A correct Case B repair must validate posted bank-backed provenance, same-house scope, available funds, outstanding limits, reversal state and locking across list/application/report paths. Cash Flow currently reads ACCEPTED pay-ins too and needs Case B consistency coverage. This work touches a financial writer and must not be described as a read-only code diff.
3. FIFO and current Aging can miss genuinely outstanding invoices with an incorrect PAID/CANCELLED stored status. This is a potential path defect. The pristine restore contains **zero** positive-debt invoices excluded by the current stored-status predicate. The two known stale ISSUED invoices are fully credited, so they are not evidence of FIFO skipping owed balances.
4. Default server dates in reports/dashboard are not explicitly Bangkok. Village Dashboard recent income formats receipt timestamps/month labels without converting timezone. That activity query also does not exclude REVERSED ledgers; this is a further display-consistency gap, separate from the corrected debt totals.
5. Legacy `/accounting/invoices/house/{id}` still uses HouseMember rather than selected-house + ACTIVE ResidentMembership. The active user-removal route deletes its legacy row; the standalone deactivation service does not and has no call site found. Aligning remaining resident read guards is preferable to maintaining divergent authority checks. Two URL aliases do not inherently imply different authorization: the six corrected report aliases share the exact handler/dependency. Prefix-specific infrastructure behavior still requires verification; CORS in `main.py` is global, not inherently limited to `/api`.

## Evidence limits and important corrections

- The snapshot has **zero POSTED ledgers with payin_id NULL**. Case B cannot currently explain a portion of the snapshot's320,818.60 unused funds or62 reconciliation households. Reclassify on fresh data before any later repair; do not infer causality from a code capability alone.
- Missing pay-in ledgers are not literally unallocatable forever: bank posting/FIFO and the accounting service can apply them. The ordinary invoice picker/apply API path is blocked. Likewise a REVERSED ledger appearing in the old list did not prove successful reversed-money allocation: existing writers reject it.
- The deployed-baseline two async guard calls are indeed ineffective. Treat this as a priority authorization defect. However earlier baseline execution of their report services failed with CreditNote schema AttributeErrors; this review does **not** establish successful production cross-house data disclosure or exploitation. Never test another resident's production data to substantiate the claim.
- Absence of a data-repair script does not prove deployment writes zero rows. Existing startup can run migrations/seeding depending on live configuration. Keep startup flags/revisions as release preconditions. Roll back the exact new code commit/artifacts without restoring an old database over later legitimate payments.
- `cash_window`'s closing/running equality is an internal consistency check, not independent financial validation; the independent SQL/raw-Statement comparisons provide that separate evidence. SQLAlchemy Numeric inputs are Decimal, so `Decimal(x)` is not automatically a precision bug in those specific paths. Float aggregate and scaling concerns remain separate improvement items.
- Missing pending-slip counts in statements is a communication gap; it is distinct from28/95's confirmed but unallocated May receipt. Add pending information separately from monetary totals and label whether it is current or restricted to the requested period.
- Credit timing by created_at and a restated view are distinct choices. With the existing schema, the report dates applied credit notes by creation time; an effective/backdated credit policy would require an explicit rule. Do not silently shift credit into the invoice month or equate latest receipt time with invoice settlement time.
