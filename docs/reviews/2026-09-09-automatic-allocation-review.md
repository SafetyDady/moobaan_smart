# ทบทวนระบบกระทบยอดอัตโนมัติหลังคำยืนยันเจ้าของ

เจ้าของยืนยัน: **ลูกบ้านไม่มีสิทธิ์เลือกบิล ระบบนำยอดไปกระทบบิลอัตโนมัติ** การแก้ข้อมูลหรือรายงานต้องคงหลักการนี้ ข้อเสนอซ่อมย้อนหลังเพียงอย่างเดียวยังไม่ปิดปัญหาเกิดซ้ำ

## ลำดับที่ทำให้ปัญหาเกิดซ้ำได้

1. ยืนยันเงิน600บาทในวันที่ยังไม่มีบิล → ledgerอยู่ แต่ยังไม่เกิดallocation
2. สร้างบิลภายหลัง → ไม่มีการดึงเงินเหลือไปชำระบิล
3. ยืนยันเงินครั้งถัดไป → autoapplyเฉพาะเงินใหม่ให้บิลเก่าสุด เงินเดิมจึงยังเหลือ

ลำดับนี้สอดคล้องกับหลักฐาน28/95ที่receiptพฤษภาคมpostก่อนสร้างบิลพฤษภาคม การใช้การผูกใหม่เฉพาะรายบ้านโดยไม่เติมtriggerยังเปิดทางให้เกิดอีก

## แผนที่ปรับ

- คงFIFOอัตโนมัติและการส่งสลิปเดิม ลูกบ้านไม่ต้องเลือกบิลหรือตอบว่าจะเอายอดไปลงเดือนไหน
- เมื่อยืนยันเงินรับ ให้พิจารณาเงินยืนยันที่ยังเหลือของบ้านตามลำดับ ไม่ใช้เฉพาะledgerที่เพิ่งสร้าง; ไม่เปลี่ยนวันที่รับจริงให้ตรงบิล
- เมื่อสร้างบิล ให้ใช้เงินยืนยันเหลือกับบิลค้างอัตโนมัติ ถ้ายังไม่มีบิลให้เก็บเงินเหลือจนเกิดบิล ไม่ต้องสร้างธุรกรรมเงินรับใหม่
- รวมหลักการเรียงบิลและเพดานเป็นทางเดียวจากflowที่ใช้อยู่ ตรวจบิลพิเศษ/เครดิตตามกฎเดิมก่อนรวมsorter ห้ามเงียบๆเปลี่ยนpriorityของบิลพิเศษเพราะcycle=0
- ออกแบบtransaction/locksให้การยืนยันเงินกับสร้างบิลพร้อมกันไม่พลาดกัน ไม่ใช้เงินก้อนเดียวสองครั้ง และretryไม่สร้างallocationซ้ำ ตรวจครบwriterpathsก่อนปรับlockorder
- การทำงานปกติเพิ่มเฉพาะallocationที่ต้องเกิดจากเงินเหลือ ไม่กลับรายการเดิมอัตโนมัติเมื่อมีreceiptย้อนหลัง การซ่อมhistoryของ28/95และกลุ่มอื่นยังต้องมีjournalและชุดbefore/afterตามpolicyระบบ

## การตรวจที่ต้องผ่านก่อน production

รับเงินก่อนบิล;บิลก่อนเงิน;เงินเก่าเหลือ+เงินใหม่;เงินล่วงหน้าหลายเดือน;จ่ายบางส่วน;ลดหนี้/บิลพิเศษ;สลิปรอตรวจ/REVERSEDไม่ถูกใช้;retry;ยืนยันเงินพร้อมสร้างบิล;หลายบ้านไม่ข้ามยอด;ข้อมูลแหล่งStatement/Pay-in/ledgerและสมาชิกไม่เปลี่ยนจากการจัดสรร

ลำดับงานใหม่คือแก้และทดสอบกลไกป้องกันเกิดซ้ำก่อน แล้วใช้policyเดียวกันพิจารณาชุดhistoryจากall-houseaudit ไม่เดินหน้าซ่อม28/95ในproductionทันทีตามข้อเสนอเก่า ไม่มีapplicationcode/DB/config/commit/push/deployในขั้นทบทวนนี้
