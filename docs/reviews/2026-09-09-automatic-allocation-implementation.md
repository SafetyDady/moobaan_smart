## ปัญหาและพฤติกรรมที่แก้

เงินที่ยืนยันก่อนสร้างบิลเคยค้างอยู่ใน ledger เพราะการสร้างบิลไม่เรียกจัดสรรเงิน และการยืนยันครั้งถัดไปใช้เฉพาะเงินใหม่ ทำให้เงินเก่ายังไม่ถูกใช้ เช่นกรณีบ้าน 28/95 เงินรับวันที่ 11 พฤษภาคมมีอยู่จริง แต่ไม่ได้ผูกกับบิล

ระบบที่แก้ทำงานอัตโนมัติเมื่อยืนยันเงินรับ และเมื่อสร้างบิล โดยใช้เงินยืนยันที่ยังเหลือของบ้านตาม `received_at, id` ไปชำระบิลค้างตาม `due_date, id` รวมบิลพิเศษด้วย ลูกบ้านส่งหลักฐานตามเดิม ไม่มีสิทธิ์เลือกบิล

- ครอบคลุม bank confirm-and-post, legacy accept ทั้ง API/service, สร้างบิลรายเดือนและบิลผ่านเส้นทางเดิม/บิลพิเศษ และ FIFO เดิม
- ใช้ eligibility เดิมของระบบ: ไม่นำรายการรอตรวจหรือ REVERSED มาใช้ ไม่เพิ่มช่องทางยืนยันหลักฐานใหม่
- ใช้ Decimal และยอดค้างหลังเครดิต/การชำระจริง ไม่อาศัยสถานะบิลที่อาจค้าง
- กรณียังไม่มีบิล เก็บเงินเหลือจนสร้างบิล; เรียกซ้ำไม่ใช้เงินซ้ำ; สร้างรายเดือนซ้ำโดยไม่มีบิลใหม่ไม่กวาดยอดย้อนหลัง
- คง Admin explicit invoice override ที่มีอยู่เดิม; resident ถูกปฏิเสธจาก API ที่สร้าง/แก้/ลบบิลหรือเลือกกระทบยอด
- กลไกอัตโนมัติเพิ่ม allocation ใหม่ ไม่กลับรายการหรือเปลี่ยนการผูกยอดเดิมเอง

## Transaction และหลักฐาน

ใช้ PostgreSQL advisory lock ต่อบ้านตั้งแต่ก่อนสร้างเงินรับ/บิล เพื่อปิดช่องว่างกรณีทั้งสองเกิดพร้อมกันแม้ยังไม่มีแถวให้ล็อก จากนั้นล็อก ledger ตาม ID ก่อน invoice ตาม ID; batch รายเดือนล็อกทุกบ้านตามลำดับก่อนล็อกแถว ทุก allocation อยู่ใน transaction เดียวกับการยืนยันหรือสร้างบิล มีการ refresh ยอดหลังรอล็อก และ rollback ทั้งชุดเมื่อเกิดข้อผิดพลาด

ไม่มี migration, dependency, frontend หรือ startup job ใหม่ วันที่และยอดบน Statement/Pay-in/ledger ไม่ถูกแก้โดยตัวจัดสรรเงิน วันที่รับเงินจริงไม่ถูกเปลี่ยนให้ตรงเดือนบิล

## ผลกระทบที่ต้องเข้าใจก่อน deploy

Deploy อย่างเดียวไม่กวาดเงินทั้งระบบ แต่ **การยืนยันเงินครั้งถัดไปหรือสร้างบิลใหม่จะใช้เงินเก่าที่เหลือของบ้านนั้นด้วย** การสร้างเดือนใหม่ทั้งหมู่บ้านจึงอาจจัดสรรเงินค้างเก่าหลายบ้านตามตัวอย่างข้างต้น การอนุมัติ release ต้องครอบคลุมพฤติกรรมนี้

กรณี 28/95: โค้ดนี้ยังไม่ย้ายเงินที่ผูกบิลพฤษภาคม/มิถุนายนไว้แล้ว ถ้า trigger จากข้อมูล snapshot ปัจจุบัน เงินรับพฤษภาคมที่เหลือจะลงบิลกรกฎาคมซึ่งเป็นบิลค้างเก่าสุด การแก้ลำดับย้อนหลังให้พฤษภาคม→พฤษภาคมยังเป็นงานแยก ต้องคำนวณ before/after ใหม่จากข้อมูลขณะทำจริง แผนซ่อมเดิมห้ามนำมาใช้โดยไม่ตรวจซ้ำ

ยังไม่ได้ทดสอบ release นี้บนหน้าจริง/production และไม่ได้รับรองการแข่งขันกับการปิดงวดบัญชี: snapshot ไม่มีงวด LOCKED การทดสอบผ่านลดความเสี่ยงในกรณีที่ตรวจ ไม่ใช่การรับรองว่าไม่มีผลกระทบทุกกรณี
