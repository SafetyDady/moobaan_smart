- ซ้อมการแก้สำเร็จจริงบนสำเนาและ commit เฉพาะสำเนา จากนั้นรันซ้ำ: ถูกปฏิเสธและไม่ใช้เงินซ้ำ
- ฟังก์ชันรายการ invoice และ access resolver ของ Admin/สมาชิก resident จริงในสำเนาให้ข้อมูลตรงกัน เหลือค้าง 600 และวันที่ชำระล่าสุดบิล พ.ค. เป็น 11 พ.ค.
- รายงานรับเงินจริงเดือน พ.ค. ทั้ง **157 บ้านไม่เปลี่ยน**; เปรียบเทียบโดยตัดเฉพาะ metadata `generated_at`

- รายการชำระเดิมเก็บ id/ยอด/เวลา/ลิงก์ครบ เปลี่ยนเฉพาะสถานะของ 286/362; ยอดรับไม่ถูกใช้เกินและไม่มีรายการข้ามบ้าน

รอบนี้เป็นการเรียกฟังก์ชัน backend และตรวจ DB จริงบน Local **ไม่ได้เปิด browser หรือทดสอบ HTTP ใหม่** หลักฐาน UI/HTTP ของ release ก่อนหน้าอยู่ในรายงาน automatic release แยกกัน

## ขั้นตอนหลังเจ้าของอนุมัติรายการข้างต้น

1. สำรอง production ใหม่และตรวจ precondition ปัจจุบันอีกครั้ง เพราะระบบกำลังใช้งาน ไม่ใช้ snapshot นี้เป็นใบอนุญาตให้ข้ามการตรวจ
2. เตรียมตัวดำเนินการ production จากแผนที่อนุมัติ ใช้ gate/locks และ transaction เดียว ตรวจงวดล็อก แหล่งเงิน ลิงก์ และเพดาน หากข้อมูลเปลี่ยนให้หยุดและคำนวณใหม่
3. เก็บ journal ก่อนเขียนและหลังเขียนพร้อม hash เชื่อมกับหมายเหตุบิล; กลับสถานะ 2 รายการและเพิ่ม 3 รายการตามขอบเขตเท่านั้น
4. ตรวจ Admin/resident, Statement, ยอดรวม และผลต่างของบ้านอื่นหลังทำจริง ก่อนสรุปผลหรือขยายไปบ้านถัดไป

ไม่ใช้ `repair_allocations.py` เก่ารัน production เพราะยังไม่รองรับ gate ใหม่ ตัวซ้อมในรอบนี้ไม่มี production connection/option และ marker ระบุ LOCAL-REHEARSAL การ rollback code ไม่ย้อนธุรกรรม และห้าม restore DB เก่าทับข้อมูลใหม่ทั้งระบบ
