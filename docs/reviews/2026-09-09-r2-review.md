# R2 — ผลแก้ไขและตรวจสอบก่อนนำขึ้น production

เจ้าของอนุมัติให้ดำเนินการตามแผน R2 หลังตรวจยืนยัน backup DB รอบนี้แก้โค้ดและทดสอบในเครื่องเท่านั้น ยังไม่ commit, push, deploy หรือแก้รายการเงินจริง แพ็กเกจ R1 เก็บไว้เป็นหลักฐานเดิม

## ผลที่ได้

| ประเด็น | ผลแก้ไข |
|---|---|
| Aging เดิมคิดหนี้เกิน | หัก ACTIVE payments และ applied credits ตามวันรับเงิน/วันสร้างเครดิต ใช้ขอบเขตสิ้นวันไทย เลิกกรองด้วยสถานะที่บันทึกค้าง |
| Aging ปัจจุบัน / FIFO | เลือกจากยอดค้างจริง แม้สถานะที่เก็บเป็น PAID/CANCELLED ผิด ไม่แก้สถานะย้อนหลังเป็นชุด |
| Receipt ไม่มี pay-in | Picker และ invoice apply API ใช้ eligibility เดียวกัน ต้อง POSTED, อ้างอิง bank POSTED ใน batch CONFIRMED, ไม่มี matched pay-in และยอด/เวลาตรง Statement; ledger NULL ที่ไม่มีหลักฐานไม่ผ่าน |
| Cash Flow | นับ POSTED ledger รวมเงินรับที่ไม่มีสลิป แทนยอด ACCEPTED pay-in; รวมเงินด้วย Decimal และใช้ขอบเขตวันไทย |
| สิทธิ์ลูกบ้าน | Legacy invoice list ตรวจบ้านที่เลือกใน token และ ACTIVE ResidentMembership เช่นเดียวกับรายงาน ไม่ใช้ legacy HouseMember ที่อาจค้าง |
| เวลาและกิจกรรม | วันเริ่มต้นรายงาน/ยอดเกินกำหนดใช้กรุงเทพฯ; กิจกรรมรับเงินตัด REVERSED และแสดงเวลาไทย; หน้า Cash Flow ตั้งวันที่โดยไม่เลื่อน 1 ม.ค. เป็น 31 ธ.ค. |
| สลิปรอตรวจ | Monthly/range JSON แยก current pending count/amount; PDF/Excel ระบุชัดว่าเป็นข้อมูลปัจจุบันทุกงวดและไม่รวมในเงินรับยืนยัน; มือถือลูกบ้านเห็นจำนวนรอตรวจและข้อความให้รอผลก่อนชำระซ้ำ; ประวัติกลุ่มรอตรวจรวม SUBMITTED |

## หลักฐานการตรวจ

- Regression **72 tests ผ่าน**: PostgreSQL 45 (25 settlement เดิม + 8 report/access + 12 R2), canonical status 12, paid-at 7, export 8 นับการเรียก unit scripts โดยตรงด้วย ไม่ใช่นับแค่ unittest discovery
- มี **13 race tests ที่ตรวจ blocking จริงด้วย pg_blocking_pids**; R2 เพิ่ม Case B credit/payment, payment/payment และ reversal/payment ไม่ทำให้เพดานยอดเสียหรือใช้เงินที่ย้อนแล้ว
- สำเนา production ครบ157บ้าน/1259บิล: matrixเดิม22,597 comparisons ผ่าน, SQL oracleรายงาน13,806 ผ่าน, HTTP/download/สิทธิ์2,375 ผ่าน, SQLตรวจ R2อีก1,895 ผ่าน (รวมเป็น40,673 checks ซึ่งหลายข้อเป็นการเทียบฟิลด์ ไม่ใช่40,673 independent test cases)
- Aging 1,413 house-months ม.ค.–ก.ย. เทียบ SQL ที่ไม่ได้เรียก model/helper: ผ่าน ยอดเดือนกันยายน **518,797.10** เทียบค่าเดิม519,997.10 แก้ส่วนเกิน1,200.00
- Admin/resident ใช้ตัวตนที่มีจริงในสำเนาและ local signing key;114 membership records,111ที่ผ่านเงื่อนไข,222 resident downloads ข้อมูลรายงานตรง Admin; legacy invoice accessเพิ่ม114checks
- Frontend production build, download handler harness และ R2 display harness ผ่าน: วันไทยใน3เขตเวลา, ตัวกรองSUBMITTED/PENDING, renderยอดและข้อความรอตรวจโดยใช้ componentจริงกับ mocked state/IO
- ตรวจภาพ PDF 28/95เดือนพฤษภาคม1หน้า และข้อมูลสังเคราะห์ยาว3หน้าครบทุกหน้า ฟอนต์ไทย/ยอด/ข้อความรอตรวจ/หัวตารางซ้ำ/เลขหน้าอ่านได้; Excelเปิดอ่านและเทียบตัวเลขกับ JSON
- ทุก public table ใน DBสำเนามีจำนวนแถวและ fingerprint ตรงกับก่อนทดสอบ ใช้ `default_transaction_read_only=on`; เทสต์การเขียนเงินอยู่ใน random schema ของ `moobaan_credit_test` เท่านั้น

## ความหมายและขอบเขตที่ต้องทราบ

1. Legacy Aging เป็น **ยอดตามวันสิ้นงวดที่คำนวณใหม่จากรายการซึ่งยังมีผล**: วันที่ใบแจ้งหนี้, วันที่รับเงิน, วันที่สร้างเครดิตแยกกัน รายการรับเดิมที่เพิ่งนำมาผูกบิลสามารถเปลี่ยนรายงานอดีตได้ ไม่ใช่ frozen period close ส่วน `/api/reports/invoice-aging` แสดงยอดค้างปัจจุบันและใช้ as_of_date คำนวณอายุหนี้เท่านั้น จึงไม่รับรองว่าย้อนเลือกเดือนแล้วสองรายงานจะเท่ากัน
2. Cash Flow AR ยังคงความหมายเดิม: บิลในช่วงที่เลือกหักเครดิตที่มีผลปัจจุบัน ไม่ได้เปลี่ยนเป็น credit-event cash statement หรือ backdateเครดิต
3. **แก้ข้ออธิบายเดิมเกี่ยวกับ Case B:** อ่านเงื่อนไขครบแล้ว `confirm_and_post` ปัจจุบันหา target_house_id จาก matched pay-in และปฏิเสธเมื่อหาไม่ได้ ก่อนเข้า branchสร้าง ledger ดังนั้น ternary `payin.id if payin else None` ไม่ได้พิสูจน์ว่าเส้นทางนี้สร้าง Case B ได้จริง R2รองรับ *ledgerแบบไม่มีpay-inที่มีหลักฐานครบอยู่แล้ว* ผ่าน picker/apply ไม่ได้เปิด writerสร้าง Case B ใหม่ Accounting serviceใช้ ledgerประเภทนี้ได้อยู่เดิม
4. สำเนามี0 POSTED no-pay-in ledger และ0ยอดค้างจริงที่ถูก stored-status predicate ตัดออก ข้อบกพร่องดังกล่าวไม่ใช่หลักฐานอธิบายปัญหา62บ้าน และไม่ได้อนุญาตให้จัดสรรเงินอัตโนมัติย้อนหลัง
5. R2 **แตะ financial writers**: invoice apply eligibility และ FIFO candidate selection คง ledger→invoice locks และเพดานยอด ไม่ควรอธิบายแพ็กเกจรวมว่าเป็น read-only code; การทดสอบกับ production snapshot ต่างหากที่ read-only
6. บ้าน28/95: รายงานแสดงรับเงินเดือนพฤษภาคม600จากledger187ได้โดยไม่ย้าย allocation เดิม; การซ่อม allocation187→881/223→1038/269→1195 และงาน62บ้านยังไม่ได้ทำบน production

## ก่อนขึ้น production

- ให้เจ้าของ/ที่ปรึกษาตรวจแพ็กเกจ R2และอนุมัติ release; ตรวจ remote HEAD/working diff อีกครั้งก่อน commit/push
- ทำ backup DBใหม่ก่อนการเปลี่ยน production ตามแผน ตรวจ checksumและrestore; backupเดิมเวลา9ก.ย.01:58น.ยังอยู่และเคยrestoreสำเร็จ
- ตรวจ live Alembic revision และ startup seed/reset flags; ไม่มี schema migration/dependency/Docker/startup changesในแพ็กเกจนี้ แต่ startupเดิมอาจเขียนDBตามconfig
- Docker Desktopเครื่องนี้ยัง buildไม่ได้; ยังไม่ได้ทดสอบ LINE OAuth/มือถือจริง/production deployment ใช้การทดสอบในเครื่องแทนข้ออ้างดังกล่าวไม่ได้
- ตรวจข้อมูลชื่อหมู่บ้าน/ข้อมูลติดต่อตาม production configก่อนแจก PDF: QAในเครื่องใช้ค่า Settingsเริ่มต้น ไม่ยืนยันค่าจริงบนproduction
- DB dumpมีข้อมูลและreferenceไฟล์ แต่ไม่ได้สำรอง object bytesของสลิป/ไฟล์แนบในR2 storage ต้องตรวจbackupแยกก่อนอ้างว่ากู้คืนหลักฐานครบทั้งระบบ
- Rollback codeด้วย revert release commitหรือredeploy artifactเดิม ห้ามคืนDBเก่าทับรายการรับเงินใหม่; data repairต้องแยกreview/backup/transaction preconditions
